3. **Slow SCSI writes. Done 2026-10-16.** HP-UX, the same tests before and after:

   | test | before | after (`c5790bc` + Main `5bd3995`) |
   |---|---|---|
   | 11 MB file write + `sync` | ~60 KB/s | 16.0 s, 680 KB/s |
   | raw read 64 KB blocks | 375 KB/s | 1.66 MB/s |
   | raw read 8 KB blocks | 240 KB/s | 1.05 MB/s |

   The causes, each fixed in turn:
   - **Main (`5bd3995`):** images are opened `O_SYNC`, and a 512-byte synchronous SD write costs 7.4 ms on this card (64 KB: 13.6 ms). It now has a write buffer.
   - **`304925f`:** MAME's chip delays on every DMA byte (~70 clocks/byte in). Removed for DMA data phases.
   - **`d8b9f8c`:** one HPS round trip per block. Disk units now ask for up to 32 blocks at a time.
   - **`c5790bc`:** MAME's 10 ms bus-free timer was the only way "connected" cleared, and HP-UX polls SSTS for bus free before every selection, so every command cost about 12 ms. It is now 400 ns.
   - **What is left:** about 180 µs a block on the SCSI/DMA side (byte-wide DMA to memory) and about 3 ms a command. Read-ahead across commands (like MacQuadra800's `scsi_cache.sv`) or DMA bursts would be the next steps.

### Open: NetBSD console/HIL (seen 2026-10-16 on `c5790bc`)

- **Panic:** one single-user boot (with `netbsd -s` typed at the loader prompt during its timeout) panicked in `cpu_configure`: 50+ `intr_dispatch: stray level 1 interrupt`, then `too many stray interrupts`. NetBSD counts a stray only when a level-1 handler exists (hil, dma) and none claims it, so level 1 stayed asserted with the 8042's data-ready bit clear. Not reproduced in two more boots (one with typing). Level-1 sources in the core: the 8042's P2.4 (OBF in flags mode), DMA channels, the 98550A interrupt (`card_intreg` level field).
- **Hang:** one multi-user boot stopped after "Updating motd." The kernel stayed alive (the syncer wrote the image every 30 s, it answered ping at its new DHCP address .54) but the console neither echoed nor answered ^T/^Q, and nothing more came from the guest on the network. Cause unknown; the console path (HIL input or wscons output) is the suspect. Next time: Ctrl+Shift+Pause (PS/2 Pause is HIL Break/Reset; with Ctrl+Shift the 8042 raises the keyboard NMI) should drop NetBSD into ddb for a `bt` and `ps`, unless HIL input itself is what died.
- **Dead keyboard at login (2026-10-17, core `7ec81f2`, 32 MB, `NetBSD92.img`):** the boot reached `login:` (13 min after the core load), the guest answered ping at .54, but typed characters never echoed (misterkvms `type`, which reaches the core: the OSD worked). The user had to power the MiSTer off, so no ddb. Together with the hang above this points at HIL input dying during or after boot, not at console output. Next: reproduce, then Ctrl+Shift+Pause for ddb, and in sim compare the 8042/HIL state after NetBSD's `hil_attach_deferred` (LPC_RECONF, autopoll, HIL_INTON).
- **Model difference found while looking:** in flags mode our UPI-41 (like MAME) keeps P2.4 as a latch that only follows OBF on the next OUT DBB or host read, so after an 8042 reset P2.4 reads 1 (IRQ 1) with OBF clear until the firmware's first output. The real part drives the pin from the OBF flag. Not shown to cause either failure.
